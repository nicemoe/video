# 跳转后画面异常调查

用户反馈：同一个 WMV 在“自动 · 软解”下跳转后花屏几秒，随后恢复。
当前核对过的依赖：KSPlayer 2.3.4、FFmpegKit 6.1.4。

## 恢复历史进度的独立路径

用户确认手动快进已流畅，但关闭后从历史进度继续仍会卡顿。检查发现播放页重建时
写死了 `accurate: true`，没有使用手动跳转的偏好，因此默认快速模式的音频预滚对齐
不会应用到这条恢复路径。现在恢复、重建和手动跳转共用播放页的 seek 入口。

另外，首次打开时 `isFirst` 和 `isSeek` 可以同时为 true。KSPlayer 原来的首次预览
分支会在目标音视频尚未就绪时调用 `readNextFrame()`，提前取走用来对齐的首帧。
现在带 seek 的首次打开只在双方就绪并对齐之后提交首帧；从头播放仍保留首次预览。

回归测试提取真实播放页的 start/seek 方法，检查默认快速和用户精准偏好、历史位置、
重建及后台不自动播放；在 ASF 时间戳测试中增加 `isFirst=true` 的首次恢复顺序。
分别恢复写死精准模式和提前预览后，测试都必须失败。此项为代码和受控测试结论，
最终恢复播放耗时仍需同一 iPhone 和 WMV 文件实测。

## 第 12 版实机记录：快速跳转的音频预滚未裁去

实机报告（iPhone17,2 / iOS 18.0）目标 1088.853 秒，快速定位：
demux 53.2 ms 完成，视频首帧 60.8 ms 入队，104.7 ms 提交显示；首帧
PTS 为 1085.785 秒。音频从 1083.538 秒开始输出，视频一直返回 `remain`，
直至约 2334.6 ms 才继续提交画面。队列有视频帧且显示层无错误；这次停顿
来自音频比视频早约 2.25 秒，不能归因于几秒的解码或显示提交耗时。

快速定位以首个可显示视频帧为共同起点，在发布可播放状态之前，原子设置音频
帧过滤边界并移除已排队的音频预滚。后续音频继续解码，早于边界的输出被丢弃；
压缩包和视频参考帧保持完整。边界相交的音频块按实际 PCM 采样裁剪，保留
边界后的数据，并用采样率作为时基保持音频时钟精度，不做额外重采样。
音频补齐可播放帧后，两只时钟同时改为实际视频起点，再提交视频、启动音频。
精准定位仍采用其目标帧过滤，纯音频播放不依赖视频起点。

回归测试使用生产队列、裁剪方法、就绪回调，重放实机 PTS 和音频先填满队列
的顺序，覆盖重新填充、边界相交、后退跳转和精准模式。真实 AudioFrame 内存
测试覆盖双声道交错/平面、44.1/48 kHz、Float32/Int16，检查裁剪后每个字节、
采样数和时间戳。移除音频裁剪后测试
必须失败。编译/测试不能替代安装后再次验证拖动体验。

## 第 11 版实机仍停顿：采集阶段诊断

用户确认关闭精准定位后，仍然声音先播放、画面停住；此前状态顺序测试不代表
实机显示已恢复。当前增加诊断，不宣称已经修复这一停顿。

在原文件中跳转一次，等待约 8 秒，打开“自动 → 复制播放诊断”。复制前不要
再次跳转，因为每次只保留最近一次跳转。报告包括设备型号、系统、构建号、
定位模式、demux 耗时、首次解码/入队、恢复输出、音画时钟与显示层提交状态。
`video_submit` 仅说明代码已提交画面，不证明屏幕实际显示；需要结合时钟、
队列和显示层错误区分解码、同步等待与显示问题。

记录只在内存保留，窗口为 8 秒，每通道每秒最多 4 个采样、总量最多 160 行。
旧跳转的解码回调不能写入新记录。无文件或网络写入，不包含视频画面、路径。
回归测试覆盖并发写入、采样频率、时间窗口及旧代次拒绝。

## 快速定位与精准定位

本地检查用户提供的 SenPlayer 6.2.3 IPA：中文资源有 `accurateSeek`（精准定位进度）
与说明“可提高调节进度的时间准确度，但可能影响定位的速度”。用户确认该选项关闭。
此前本项目始终打开 `isAccurateSeek`，两者定位策略不同。

用户拖动进度、手势和快进按钮现在默认快速定位，从前一个可播放关键帧开始，允许位置
略早于目标。解码菜单保留持久化的“精准定位（可能较慢）”开关。恢复历史进度、旋转后
重建播放器、切换解码器与手动跳转统一使用这个偏好；快速模式可能从稍早的关键帧继续。
每个待执行跳转同时保存目标和定位模式；仅在该跳转开始时应用模式，后续请求不改变
正在执行的跳转。两种模式共用目标帧就绪门槛和参考帧保护。

IPA 主可执行文件 cryptid=1，无法直接检查其跳转代码；FFmpeg 相关框架的 plist 版本
均为占位的 1.0，不能据此识别真实 FFmpeg 版本。未将对方程序代码或资源引入本项目。

## 声音提前恢复、画面仍在预解码

上一版实机反馈：快进后声音先播放，画面停住。代码中 `KSMEPlayer.seek`
只修改 `playbackState`，没有清除前一时间线的 `loadState == .playable`。
`MEPlayerItem` 的 completion 在 demux seek 和清队列之后调用，并不等待目标
视频解码。App 此时调用 play，旧 playable 状态允许音频先启动；缓冲检查在
已 playable 的分支只检查包和帧是否都为空，队列有压缩包就不会阻止播放。
因此上一版新增的本地目标帧就绪条件可以被绕过。

修复：seek 开始立即将 loadState 改为 loading；demux 定位和清队列期间不发布
就绪状态。各轨道达到原有的目标帧条件后，先提交目标视频帧，再恢复音画输出。
暂停状态下跳转只更新画面、不自动播放。显示 timebase 保留微秒精度，避免
此前取整到秒。保留全部参考包和已验证的队列代次修复。

回归测试从当前生产源码提取 seek、状态属性、缓冲判断、容量回调及输出开关方法，
使用可控制的音频/显示设备与 demux 完成事件，覆盖 100 次音频先就绪的序列、
旧队列采样、暂停预览、纯音频、时间精度。去掉 loading 重置后，同一测试必须失败。
这验证状态顺序，不替代 iPhone 的耗时测试，也不能证明已达到 SenPlayer 的速度。

## 跳转停顿优化

用户确认队列修复后花屏消失，但与 SenPlayer 播放同一个文件相比仍有跳转停顿。
KSPlayer 官方 README 列出 SenPlayer 使用其 SDK；未获得 SenPlayer 的具体播放实现，
不把它的参数当作已知事实。

本次修正三条可在源码确认的额外开销：

- 非字节 seek 直接把绝对目标转成微秒，避免分别截断当前秒数和跳转差值。
  例如从 1001.25 跳到 1002，旧计算实际定位到 1001，可能多退一整组关键帧。
- 精确跳转的预解码视频继续进入解码器和滤镜，保留参考链；在创建 CVPixelBuffer、
  拷贝/转换像素之前判断显示时间，避免处理必然丢弃的画面。
- 本地文件 seek 在各轨道至少有两帧可播放数据时允许恢复，不再等待通用的前向缓存量。
  正常播放的缓冲、网络源策略继续使用原有条件。同时移除引擎层重复暂停和完成后的第二次显示队列清空。

同一原文件的桌面对照使用 PyAV 12.3.0，模拟旧/新定位计算及转换前/后过滤。
每个目标比较连续 5 帧的完整可见 YUV 像素摘要，五个目标均一致：

| 起点 → 目标（秒） | 解码帧数：旧 → 新 | 像素转换次数：旧 → 新 |
| --- | ---: | ---: |
| 59.75 → 60.2 | 88 → 88 | 88 → 5 |
| 299.25 → 300.5 | 96 → 96 | 96 → 5 |
| 599.95 → 600.5 | 122 → 32 | 122 → 5 |
| 1001.25 → 1002 | 101 → 11 | 101 → 5 |
| 1001.25 → 1002.8 | 35 → 35 | 35 → 5 |

帧数包含目标处的 5 帧。桌面使用 libswscale 转 NV12，不能代表 iOS 的 CVPixelBuffer
转换耗时，也不包含音频缓冲、屏幕刷新或手机 I/O；不据此宣称与 SenPlayer 等速。
关键帧到目标位置之间必要的解码仍会保留，实机需验证短距离跳转、跨关键帧跳转及连续拖动。

## 跳转丢失首包的线程竞态（已验证花屏修复）

上一版只修正追帧时丢压缩包的问题，用户实测每次拖动进度仍然花屏。
继续检查 KSPlayer 2.3.4 的 `AsyncPlayerItemTrack.decodeThread`，发现：
解码线程阻塞在 `packetQueue.pop(wait: true)` 时，seek 清空队列并设为
`.flush`；线程被唤醒后可能先取走新时间线的首包，再因 `.flush` 判断而
丢弃它。先取包、后检查状态的顺序会丢掉跳转后需要的关键帧。

本项目现在直接依赖 `Vendor/KSPlayer` 中固定版本源码，以便修正底层：

- 队列每次 flush 增加代次；旧的等待只能返回空，不能拿走新代次的包。
- 在队列锁内、移除包之前检查解码器是否需要 flush，保留新首包。
- 在输出队列锁内检查解码所属代次、过滤精确跳转前的帧；seek 原子更新
  目标时间并清空显示队列，避免旧的解码回调向新时间线提交画面。
- 沿用自动硬解/软解，不增加固定延时或遮罩来掩盖错误画面。

原文件的受控实验：跳转至 1002 秒（截图 16:42），正常 seek 的首个
关键帧为 1001.768 秒。只丢这个关键帧，之后 **89 帧**的可见像素与
正常解码不同（1001.801～1004.738 秒），1004.771 秒的下一个关键帧
恢复。600 秒位置同样产生 89 帧差异，且没有 corrupt 标志或解码报错。
原始媒体保持本地，未上传。实验能解释症状，但不是 iPhone 线程现场记录。

`SeekQueueRegressionTests.swift` 编译实际生产队列，检查首包保留、旧回调
拒绝，并覆盖 300 次并发 seek/wait 调度。iOS 完整编译和归档由 Actions 验证；
手机上每次拖动是否彻底恢复仍需实机确认。

## 追帧丢压缩包的问题（上一版修正）

KSPlayer 的 `videoClockSync` 在视频落后且显示队列只剩一帧时，会返回
`dropGOPPacket`。`MEPlayerItem.getVideoOutputRender` 按 `!packet.isKeyFrame`
删除压缩包，直到关键帧或当前队列为空。非关键帧不等于非参考帧；队列在
GOP 中途耗尽后，新入队的帧仍可能引用已经丢弃的画面。

本项目通过 `ReferenceSafePlaybackOptions` 将 `dropNextPacket` 和
`dropGOPPacket` 改为 `dropNextFrame`。时间同步和解码继续进行，只跳过
已经完整解码的显示帧，不破坏压缩视频的参考链。自动硬解/软解策略保持。
这是对已确认风险的修正；原始 WMV 的对照实验见下文，iPhone 上的实际播放仍待验证。
代价是解码器必须继续处理参考帧，性能不足时追赶音频可能较慢。

## 对照的上游实现

- [mpv vd_lavc.c](https://github.com/mpv-player/mpv/blob/master/video/decode/vd_lavc.c)：
  `prepare_decoding` 中精确跳转使用 `AVDISCARD_NONREF`；
  `reset_avctx`/`send_packet` 在硬解重置后等待关键帧。
- [ijkplayer ff_ffplay.c](https://github.com/bilibili/ijkplayer/blob/master/ijkmedia/ijkplayer/ff_ffplay.c)：
  seek 后清包队列、发送 flush 包，解码和显示检查 serial，拒绝旧时间线的帧。
- [VLC video.c](https://github.com/videolan/vlc/blob/master/modules/codec/avcodec/video.c)：
  flush 清理解码器；显示入口可过滤 `AV_FRAME_FLAG_CORRUPT`，受丢帧和显示损坏帧设置控制。
- [KSPlayer KSOptions.swift](https://github.com/kingslay/KSPlayer/blob/2.3.4/Sources/KSPlayer/AVPlayer/KSOptions.swift)：
  `videoClockSync` 的追赶策略。
- [KSPlayer MEPlayerItem.swift](https://github.com/kingslay/KSPlayer/blob/2.3.4/Sources/KSPlayer/MEPlayer/MEPlayerItem.swift)：
  `getVideoOutputRender` 的压缩包丢弃实现。

## 原始 WMV 对照实验

对用户提供的本地文件进行只读分析：ASF/WMV3、1920×1080、30000/1001 fps，
时长 2722.133 秒，关键帧间隔约 3.003 秒。未上传视频或导出画面。
实验环境为 Windows、PyAV 12.3.0，libavcodec 60.31.102 / libavformat 60.16.100
（FFmpeg 6.1 系列）。按时间戳逐帧比较可见像素的 SHA-256，排除缓冲区 padding。

| 跳转位置 | 正常跳转与提前解码的差异帧 | 中途丢 8 个非关键压缩包后的差异帧 | 只丢 8 个显示帧后的差异帧 |
| --- | ---: | ---: | ---: |
| 60 秒 | 0 / 438 | 79 / 430 | 0 / 430 |
| 300 秒 | 0 / 438 | 80 / 430 | 0 / 430 |
| 600 秒 | 0 / 374 | 54 / 366 | 0 / 366 |

第一组异常从 60.794 秒持续到 63.396 秒，63.430 秒关键帧恢复；
另外两组也在下一个关键帧恢复。压缩包丢失后的异常帧均没有 `is_corrupt`
标记，解码器也没有报错，因此只检查解码失败或损坏标记不能解决这条路径。

这是模拟上游队列在 GOP 中途耗尽的控制实验，证明该文件在此丢包策略下
会产生约 1.8～2.6 秒的错误解码输出，并证明丢显示帧不改变后续解码结果。
实验使用 PyAV 的 seek 接口，未运行 iOS 的 KSPlayer 渲染和音画同步线程，
不能据此断言手机上的所有花屏都已经解决。

GitHub Actions 验证 Swift 编译、现有回归测试和 iOS 归档。
仍需在 iPhone 上验证同一 WMV：单次快进、连续跳转、后退、暂停时跳转。
